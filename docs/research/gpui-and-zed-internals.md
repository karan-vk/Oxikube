# GPUI research report for Oxikube (as of 2026-10-03)

No clones were made (plan mode was active); everything was read through `gh api`, `curl` to raw.githubusercontent.com and crates.io, WebFetch and WebSearch, from `zed-industries/zed@main` (pushed 2026-10-03), the crates.io API, or the repos named in each section. Five chunks as delivered, plus the Zed internal-dependency report at the end.

## HEADLINE FINDINGS
1. crates.io `gpui` 0.2.2 (2025-10-22) is frozen. Zed main has since split GPUI into several crates. The de-facto way to pin GPUI today is the weekly `gpui-pre` snapshot crates, published by the gpui-component maintainer (not by Zed).
2. Nearly every Zed crate above GPUI is GPL-3.0-or-later (ui, theme, settings, workspace, editor, terminal, terminal_view, picker, acp_thread, extension_host...). They are patterns to copy, not libraries to depend on, unless Oxikube is GPL.
3. Two Kubernetes clients on GPUI already exist and are close to our scope: Kubyl (BirknerAlex/kubyl, created 2026-09-24) and Periscope (abdulk1/periscope). Both avoid Zed's GPL crates. Their handoff logs are the best "what bites you" source (lessons in chunk 5).
4. ACP Rust SDK is now `agent-client-protocol` 2.2.0 (stable protocol v1, draft v2), fully re-architected vs 0.x. Antigravity is in the ACP registry (binary distribution).

## 1. HOW TO DEPEND ON GPUI

State of the crates (crates.io API):
- gpui 0.2.2, 2025-10-22, Apache-2.0, frozen. (0.2.1 2025-10-14, 0.2.0 2025-10-09)

- gpui-pre 0.3.7, 2026-09-28, "snapshot of zed@1a28cff", Apache-2.0. Weekly releases since 2026-09-03: 0.3.2, 0.3.3 (09-03), 0.3.4 (09-07), 0.3.5 (09-14), 0.3.6 (09-21), 0.3.7 (09-28). ~70k downloads.

- gpui-component 0.7.0 (2026-09-28), gpui-kit 0.7.0, gpui-base 0.7.0, gpui-wry 0.7.0, gpui-component-macros 0.7.0, gpui-kit-assets.

Who publishes gpui-pre-*: NOT Zed. `gpui-pre` sole crates.io owner is `huacnlee` (Jason Lee, gpui-component maintainer). Published by gpui-kit's `release-gpui.yml` workflow (weekly) using `script/bump-gpui.ts`, which: renames crates to gpui-pre-* while keeping library names (so `use gpui::*` still works), drops git-only optional deps and their features, relaxes exact external pins to caret, swaps `reqwest` for a fork (gpui-pre-reqwest), rewrites a few files. Each release's description names the Zed commit. Snapshots are of Zed `main`, not of a Zed stable release. Each snapshot is built/tested against gpui-kit before publish. gpui-kit PR #3283 ("Update GPUI to gpui-pre 0.3.7") shows the process (and that 0.3.7 needed 3 publish attempts; bench Criterion 0.5 vs 0.8 mismatch left as follow-up).
Third-party summary (yicheng47/runner issue #733): "Zed owns the gpui crate names on crates.io and publishes only occasionally... Zed's crates.io gpui is still frozen at 0.2.2... The exit is cheap: a Zed git dependency at the commit a snapshot names is the same code." Cost: third-party publisher, rewritten manifests, snapshots of main.

Latest Zed tags/releases (gh api): stable v1.22.0 (2026-09-30), v1.21.0 (2026-09-23), v1.20.2 (2026-09-17); pre-release v1.23.1-pre (2026-09-30), v1.23.0-pre, v1.22.0-pre. Zed reached 1.0 in April 2026 (WebSearch result). Zed repo clone ~516 MB (runner #733) -> reason to avoid git deps in CI.

gpui_platform features: font-kit (REQUIRED on macOS for glyphs; without it text lays out but renders nothing), wayland / x11 (required on Linux; also compile renderer + text), runtime_shaders (macOS: compile shaders at startup, no Xcode Metal toolchain needed; Kubyl enables it), test-support, screen-capture, inspector, bench-support. Windows: no features needed (Win32 + DirectWrite).
gpui-pre default features: font-kit, wayland, x11, windows-manifest.
Breaking changes vs 0.2.2 (from runner port notes): app starts from gpui_platform::application(); Corner -> Anchor; Window::focus/blur take cx; ScrollHandle::max_offset() returns a Point; BoxShadow and Menu literals gain a field; inactive windows throttled to ~30 fps; new macOS titlebar-drag option; text rendering mode option.

Recommendation: exact `=` pins on one gpui-pre snapshot (the one gpui-component pins: gpui-pre =0.3.7 for gpui-component =0.7.0). Bump all gpui-pre-* + gpui-component/base/assets together in a dedicated PR. Commit Cargo.lock, consider vendoring. Document exit: Zed git dep at the `zed@<sha>` named in the snapshot description. Zed's own [patch.crates-io] entries (async-task, calloop, async-process, notify...) do NOT reach dependents; check in a spike whether macOS/Windows misbehave without them (runner #733 scope item 2).

Adopt vs build in-house: ADOPT for v1 behind our own wrapper crate, keep an escape hatch.
For: Apache-2.0; largest ecosystem on the same gpui-pre types (Kubyl, dbflux, termy, tty7, zedis); table/dock/tabs/resizable/command palette/forms/dialogs/notifications/theming/editor/charts exist; rebuilding Zed's ui/workspace/picker/editor equivalents would be many months and Zed's are GPL anyway (ui 997 KB, workspace 1.9 MB, editor 6.5 MB source).
Pitfalls: (a) API churn: 8 releases in 8 weeks, crate rename, breaking changes listed in release-notes.md (Root now owns dialog/sheet/notification layers; Plot moved to gpui-base with tidied API; questionnaire choose() behaviour change; 0.6.5 yank). (b) Exact pin to one gpui snapshot: cannot move gpui independently; a GPUI fix newer than the snapshot needs a patched/vendored copy (dbflux vendors vendor/gpui-pre, vendor/gpui-base, vendor/gpui-component; tty7 uses a fork branch `l0ng-ai/gpui-component` branch tty7). (c) Root layer gotcha in 0.6.6: root view had to render Root::render_*_layer itself. (d) Resizable panels work in absolute pixels -> UI zoom needs conversion. (e) Single maintainer concentration + one commercial sponsor (Longbridge). (f) No interactive Windows/Linux evidence from Kubyl/Periscope (compile + unit tests only). (g) a11y still needs per-platform verification.
Mitigation: wrap gpui-component behind our own `oxikube_ui` crate (Kubyl's `kubyl_ui` does this), own design tokens, own TableDelegate/editor trait boundaries, vendor if needed.

## 3. GPUI CORE CONCEPTS

Docs/examples to cite: zed/crates/gpui/README.md; module docs `src/_ownership_and_data_flow.rs` (best intro) and `src/_accessibility.rs`; examples in crates/gpui/examples/: hello_world, uniform_list, list_example, data_table, input, drag_drop, set_menus (actions + menus), testing, tab_stop, focus_visible, image_gallery, image_loading, gif_viewer, painting, text, text_layout, text_wrapper, svg, animation, gradient, shadow, opacity, popover, anchor, scrollable, tree, window, window_positioning, window_shadow, window_movable, system_notifications, a11y, layer_shell, view_example, toggle_headless, move_entity_between_windows, grid_layout, active_state_bug, mouse_pressure, paths_bench, pattern, on_window_close_quit, ownership_post. README says "best way to learn is to read the Zed source code". Better guides: gpui-kit's website/docs/*.md (entity, render, focus, global, action, task, event, test, view-cache, render-once, text-system, paint, element, element_id, window, multi-window...). gpui crate source is 144 files / 3.4 MB.

Concepts (type names from gpui/src):
- App / Application / AppContext: `gpui_platform::application().run(|cx: &mut App| ...)`. App owns all state: cx.open_window, cx.new, cx.global::<G>(), cx.set_global, cx.update_global, cx.observe_global, cx.bind_keys, cx.on_action, cx.set_menus, cx.spawn, cx.text_system(), cx.activate(true), cx.observe_new. `AppContext` trait = create/update entities. `AsyncApp` = async handle. `Application::with_assets(impl AssetSource)`.
- Entity<T> / WeakEntity<T> / Context<T>: Entity is a refcounted handle (like Rc) to state owned by the App. Access: `entity.update(cx, |t, cx| ...)`, `entity.read(cx)`. `Context<T>` wraps App + entity services: notify(), emit(), observe, subscribe, observe_self, on_release, observe_release, spawn, spawn_in, listener(), processor(), entity(), weak_entity(), defer_in, focus_view/focus_self, observe_window_bounds/activation/visibility/appearance, observe_keystrokes.
- Window: per-window context (focus, bounds, actions, painting, render_to_image).
- Render trait / views vs elements: a view is an Entity<T: Render>; `fn render(&mut self, window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement`. `RenderOnce` + `#[derive(IntoElement)]` for stateless components. Elements: low-level `Element` trait (request_layout / prepaint / paint) for custom elements (editor, terminal). Built-ins: div, img, svg, canvas(prepaint, paint), uniform_list, list(ListState, ...), anchored, deferred, surface, animation, text/StyledText, container_query, image_cache.
- div() styling: Tailwind-like fluent API (Styled / FluentBuilder / InteractiveElement / StatefulInteractiveElement): `div().flex().flex_col().gap_3().bg(rgb(0x505050)).size_full().justify_center().items_center().rounded_md().border_1().border_color(..).shadow_lg().text_xl().text_color(..).hover(|s| ..).id("x").on_click(..)`. Layout engine: taffy (=0.13.0, flex + grid). StyleRefinement via the `refineable` crate.
- Actions + keymaps: `actions!(namespace, [A, B])` (unit structs); `#[derive(Action)]` + `#[action(namespace = x)]` for data-carrying actions; `register_action!`. Handlers: `cx.on_action(fn)` global, or `.on_action(cx.listener(..))` on elements. Bindings: `cx.bind_keys([KeyBinding::new("cmd-q", Quit, Some("Context"))])` matched against `.key_context("...")`. `cx.set_menus(vec![Menu{..}])` for native menu bar. Zed's keymap JSON: `[{ "context": "Editor && mode == full", "use_key_equivalents": true, "bindings": { "cmd-shift-w": "workspace::CloseWindow", "enter": "menu::Confirm" } }]` (assets/keymaps/default-macos.json; also default-linux.json, default-windows.json, vim.json). Dispatch goes from focused element up the key-context tree (key_dispatch.rs, keymap/).
- Focus: FocusHandle, Focusable trait, `.track_focus(&handle)`, `window.focus(&handle, cx)`, tab_stop.rs, focus_visible.
- Global state: `impl Global for T {}`; cx.set_global / cx.global::<T>() / cx.update_global / cx.observe_global::<T>().
- Async: `cx.spawn(async move |this, cx| ..)` runs on ForegroundExecutor (main thread, can touch entities); `cx.background_spawn(fut)` / BackgroundExecutor::spawn on thread pool. Both return `Task<R>`: dropping a Task CANCELS it; `.detach()` lets it run. Types in gpui/src/executor.rs: BackgroundExecutor (spawn, spawn_with_priority, timer, now, block_on, scope, num_cpus), ForegroundExecutor (spawn, spawn_with_priority, spawn_when_idle, block_on, idle_time_remaining). GPUI executors are NOT tokio. `gpui_tokio` (Apache-2.0): `gpui_tokio::init(cx)` (own 2-worker multi-thread runtime) or `init_from_handle(cx, handle)`, then `Tokio::spawn(cx, fut)` returns a GPUI-awaitable task (used by Zed's extension host to run wasmtime futures). Kubyl wraps it as `spawn_kube()` with abort-on-drop.
- Subscriptions/observations: `cx.observe(&entity, |this, entity, cx| ..)` fires on cx.notify(); `cx.subscribe(&entity, |this, emitter, event, cx| ..)` with `impl EventEmitter<E> for T` + `cx.emit(e)`. Each returns `Subscription` (drop = cancel; `.detach()` = keep). `_in` variants take Window. `observe_global`, `observe_new`, `observe_release`.
- Virtualised rendering: `uniform_list(id, count, cx.processor(|this, range, window, cx| items))` fixed row height, cheapest (examples/uniform_list.rs); `list(ListState, render_fn)` variable heights (elements/list.rs, examples/list_example.rs). gpui-component adds VirtualList + Table.
- Text rendering/shaping: `TextSystem` (shape_line / shape_text, line wrapper, text runs). Backends: macOS CoreText via `zed-font-kit` (0.14.1-zed); Linux `cosmic-text` 0.19 + `swash` in gpui_wgpu; Windows DirectWrite (direct_write.rs). Fonts: `cx.text_system().add_fonts(...)` (examples use example_support::load_fonts). IME via `EntityInputHandler` / input.rs.
- Images: `img(path | uri | Arc<RenderImage>)` with pluggable image cache (elements/image_cache.rs), `svg()` via resvg/usvg, GIF (gif_viewer example), `surface` for video frames (core-video on macOS).
- canvas / painting: `canvas(prepaint_fn, paint_fn)`, PathBuilder (lyon), gradients, shadows, animation.rs + spring.rs. Assets: `impl AssetSource` to embed SVG icons/fonts.
- Window features: WindowOptions { window_bounds, titlebar, window_decorations (Client/Server), ... }, multi-window, `layer_shell` example (Wayland), system notifications, screen capture (feature screen-capture, scap).

Platform status (from Cargo manifests in zed main):

## 5. ZED'S THEME SYSTEM

Schema: https://zed.dev/schema/themes/v0.2.0.json. Registry: github.com/zed-industries/extensions (1,913 stars, pushed 2026-10-02). `extensions.toml` maps ID -> `{ submodule = "extensions/<id>", path = optional subdir, version }`; extensions are git submodules; CI (justfile, dangerfile.ts, src/, vite) builds and publishes to the Zed extension CDN (via extension_cli); has AI_POLICY.md + CONTRIBUTING.md.

Host (extension_host/src/wasm_host.rs; wasmtime 48, wasmtime-wasi p2): shared `wasm_engine()` OnceLock with `Config::wasm_component_model(true)`, `epoch_interruption(true)`, incremental compilation cache `IncrementalCompilationCache` (mini-moka LFU/LRU capped at 32 MB; comment: extensions "turn into roughly 512kb in the cache"); a background task increments the engine epoch; per-extension `wasmtime::Store` with `set_epoch_deadline(1)` + `epoch_deadline_async_yield_and_update(1)` (cooperative yielding, runaway extensions can't block); WASI context per manifest (`build_wasi_ctx`; extension working dir); extension calls run via `gpui_tokio::Tokio::spawn` (bridge between the wasm host and GPUI); `WasmState` implements WasiView/HasData; capability_granter.rs; headless_host.rs (remote server). What a Kubernetes-client plugin system should borrow:
- WIT components on wasmtime for sandboxed, language-agnostic plugins; versioned `since_vX` worlds kept side by side so old plugins keep working.
- Declarative manifest (extension.toml) for non-code contributions (themes, icon themes, resource column definitions / CRD printers, action definitions, kubeconfig providers, snippets/templates).
- Capability grants with allow-lists (network hosts, processes, filesystem paths; for K8s additionally kube API verbs/resources/contexts, read-only vs write).
- Epoch interruption for runaway plugins; bounded compile cache.
- Registry repo with PR-based submodule publishing + CDN builds.
Caveat: Zed extensions cannot add UI; a K8s client wanting plugin-provided views needs another mechanism: a declarative UI schema, gpui-kit's `gpui-shell` (JS runtime via rquickjs hosted by Rust with capabilities granted one at a time; docs/gpui-shell.md; crates/shell, crates/component-shell), or WIT exports returning a UI-tree description.

Client usage (examples/yolo_one_shot_client.rs):
```rust
use agent_client_protocol::{AcpAgent, Agent, ConnectionTo};
use agent_client_protocol::schema::ProtocolVersion;
use agent_client_protocol::schema::v1::{ContentBlock, InitializeRequest, NewSessionRequest, PromptRequest, RequestPermissionOutcome, RequestPermissionRequest, RequestPermissionResponse, SelectedPermissionOutcome, SessionNotification, TextContent};
agent_client_protocol::Client.builder()
  .on_receive_notification(async move |n: SessionNotification, _cx| { /* ..n.update.. */ Ok(()) }, agent_client_protocol::on_receive_notification!())
  .on_receive_request(async move |req: RequestPermissionRequest, responder, _conn| { responder.respond(RequestPermissionResponse::new(RequestPermissionOutcome::Selected(SelectedPermissionOutcome::new(option_id)))) }, agent_client_protocol::on_receive_request!())
  .connect_with(AcpAgent::from_str("cmd args")?, |conn: ConnectionTo<Agent>| async move {
      conn.send_request(InitializeRequest::new(ProtocolVersion::V1)).block_task().await?;
      let s = conn.send_request(NewSessionRequest::new(cwd)).block_task().await?;
```

Protocol shape (schema/v1/meta.json):
- Transport: JSON-RPC 2.0 over agent stdio (or HTTP/SSE/WebSocket crates); `$/cancel_request` for cancelling requests.
- Agent methods (client -> agent): initialize, authenticate, session/new, session/load, session/set_mode, session/set_config_option, session/prompt, session/cancel, session/list, session/delete, session/resume, session/close, logout.

Capabilities: agents advertise AgentCapabilities (prompt: image/audio/embedded context; session load/list/resume/close...), clients advertise ClientCapabilities (fs read/write, terminal, auth terminal, elicitation form/url, session config options bool, compaction, notices). Content = ContentBlock (text, image, audio, resource link, embedded resource). Docs under docs/protocol/v1: initialization, authentication, session-setup, prompt-turn, tool-calls, file-system, terminals, content, agent-plan, session-modes, session-config-options, session-list, session-delete, slash-commands, elicitation, cancellation, error, extensibility, transports.

## 10. EDITOR OPTIONS FOR A YAML/JSON EDITOR

Zed's `editor` crate: ~6.5 MB Rust source in 76 files (editor.rs 476 KB, element.rs 561 KB, display_map/block_map.rs 229 KB, inlays/inlay_hints.rs 255 KB, split.rs 194 KB, editor_tests.rs 1.6 MB); depends on ~45 Zed crates (project, language, multi_buffer, lsp, workspace, settings, theme, theme_settings, ui, ui_input, db, client, git, rpc, dap, task, telemetry, snippet, vim_mode_setting, zed_actions...). GPL-3.0-or-later. Realistically NOT reusable: licence forces GPL-3, and it can't be extracted without dragging in `project` (4.2 MB) etc.

Options:
A. Zed `editor` crate - GPL-3; very high effort; everything works but forces GPL + tied to Zed internals.
B. gpui-component `Editor`/`EditorState` (Apache-2.0) - low effort; tree-sitter-yaml/json highlighting, line numbers, folding, search/replace, multi-cursor, undo, DiagnosticSet squiggles, LSP completion/hover types, decorations; risks: churn, limited inline widgets, undocumented soft-wrap/indent guides, 200K-line claim unverified.
C. Own editor on ropey + tree-sitter + custom Element - high effort (months to reach B's parity); IME, selection, undo, wrap, a11y are all hard.
D. Lighter: read-only highlighted view (gpui-component highlighter / syntect) + small edit box - low effort, not a real editor.

Honest assessment: B for v1. Kubyl is an existence proof with nearly our scope: its YAML editor (shipped 2026-09-24; plans/04-yaml-editor.md) has schema validation against the cluster's OpenAPI v3 (incl. CRDs), hover docs, completion, diff vs live object, dry run, server-side apply, secrets masking, managedFields toggle. Built on gpui-component `EditorState` with the `tree-sitter-yaml` feature; they did themselves:
- YAML parsing with byte spans via `granit-parser` 1.3.0 (YAML 1.2 core, spanned paths) - NOT tree-sitter - plus schema (merged $ref/allOf view of OpenAPI v3 nodes, per-cluster+group-version cache dropped on DiscoveryChanged), validate (unknown fields, wrong types, enums, required, patterns, x-kubernetes-* hints), intel (hover + completion), diff (comment-insensitive line diff ignoring server-managed fields; `similar` for three-way merge), render (object -> text, keys sorted like kubectl), apply (SSA with field manager `kubyl`, dry-run, force-conflicts, 415 fallback to replace/merge patch, server errors placed on their fields), templates.
- Diagnostics via the editor's `DiagnosticSet` (squiggles); gutter change markers, code lenses and end-of-line messages painted by a `canvas` over the editor using `EditorState::range_to_bounds`; the status block dimmed with a decoration collection; keybindings use modifier keys only because the buffer takes text; editor toggles in a 300 px sidebar; bottom panel for diff/problems/history.
- Their stated risks: "gpui-component's editor may lack features we need (diagnostics rendering, inline widgets). Budget for extending it or upstreaming changes." and "YAML round-tripping must keep comments and key order in the user's buffer (edit text, not re-serialize)."
Expect to hit with B: inline widgets / block decorations, soft wrap + indent guides, onEnterRules, richer LSP. Plan to upstream or vendor (dbflux and tty7 vendor/fork gpui-component). Verify early: large-file behaviour (multi-MB `kubectl get -o yaml` dumps / big CRDs), IME on Windows/Linux, undo behaviour under live external updates (Kubyl shows a banner "Object changed on server - merge / reload / keep mine"; clean buffers refresh silently).
Recommendation: B for v1 behind our own `YamlEditor` view + trait boundary; do not take A; revisit C only if B's gaps become blocking.

## RISKS

- API churn (HIGH): GPUI has no stable API; gpui-pre snapshots change weekly; crate layout already moved (gpui -> gpui_platform + gpui_macos/_linux/_windows/_wgpu); gpui-component had ~8 releases in 8 weeks, a crate rename and breaking changes. Budget a recurring upgrade task; isolate upgrade PRs.
- Single-publisher dependency (MEDIUM-HIGH): gpui-pre-* has one crates.io owner (huacnlee) and a custom rewrite script; a snapshot could be yanked (cf. gpui-ce 0.3.2/0.3.3 yanked 2026-08-28) or publishing could stop. Mitigate: exact pins, committed Cargo.lock, vendoring, documented git-rev fallback.
- GPL contamination (HIGH if mishandled): all high-value Zed UI crates are GPL-3.0-or-later; copying code (not just reading) pulls the licence. Also check licences of any third-party theme content before bundling.
- Platform maturity (MEDIUM): macOS strong; Linux (wgpu/Vulkan, Wayland client-side decorations) and Windows (DX11) are used by Zed daily, but both third-party K8s apps have only compiled/tested them in CI. IME, HiDPI, window chrome, Wayland app_id/.desktop are the usual trouble spots.
- Accessibility (MEDIUM): AccessKit integration exists but Periscope reported no screen-reader support (on older versions); re-test on 0.3.7/0.7.0 against our requirements early.
- Editor depth (MEDIUM): gpui-component editor lacks documented soft-wrap/indent guides, inline widgets, richer LSP; Kubyl had to build overlays itself; large-file numbers are vendor claims.
- Table performance claims (LOW-MEDIUM): "hundreds of thousands of rows" and "5k/10k pods at 60 fps" are not independent benchmarks; uniform_list requires fixed row heights; frame-time profiling is on us.
- ACP churn (MEDIUM): SDK went 1.0 -> 2.2 in 3 months with a re-architected API + draft v2; adapters version fast (claude-acp 0.85.1, codex-acp 2.1.1, gemini 0.62.0). Pin v1 stable + exact crate version; treat registry JSON as a runtime input with schema validation. Note claude-acp and antigravity-acp licences are "proprietary" in the registry (redistribution/bundling needs a check; spawning via npx/binary download is how Zed does it).
- Build/packaging cost (MEDIUM): GPUI-heavy debug builds are slow (Zed sets opt-level=3 for proc-macros, tree-sitter, taffy, resvg, wasmtime in dev); big dependency tree; Zed repo clone ~516 MB (reason to use crates.io snapshots); Windows needs MSVC + Spectre libs + (if wasmtime) CMake; Linux needs Vulkan + wayland/xkbcommon/x11-xcb/fontconfig/alsa dev packages; unsigned Windows/Linux artefacts trigger SmartScreen/packaging work.
- Maintainer / AI-authored code risk (LOW-MEDIUM): parts of gpui-kit and both K8s reference apps are heavily AI-assisted (AGENTS.md/CLAUDE.md, "prepared with Codex"); quality appears fine but review before relying on edge-case behaviour. The K8s reference apps are < 1 month old with 0 stars each (Kubyl: created 2026-09-24): treat as design references, not proven products.

Not verified: gpui_macos text/shader internals; Windows/Linux interactive behaviour of the 0.3.x stack for third-party apps; the exact 200K-line editor claim; the ACP v2 draft's migration impact.

# Zed internal-dependency report (tag v1.22.0)

Only `[dependencies]` and `[target.*.dependencies]` were read, dev-dependencies excluded. The tag path worked, so there was no fallback to main. 165 Cargo.toml fetches and a BFS over every dependency whose root-workspace entry is a `path = ...`. Licences as of v1.22.0.

## Key takeaways
- The workspace has 252 members and 232 path-dependency crates. The workspace sets `publish = false`.
- All GPL-3.0-or-later except the gpui family. Only gpui and its low-level helper crates are Apache-2.0: gpui, `util`, `collections`, `sum_tree`, `refineable`, `zlog`, `http_client`, `scheduler`, `path`, `ztracing`, `gpui_util`, `gpui_macros` and `extension_api`.
- The "pure UI" crates are cheap. `ui`, `theme`, `menu`, `zed_actions`, `release_channel`, `settings_content`, `db` and `sqlez` pull in at most 23 crates, and none of them drag in `project`, `client`, `editor`, `language`, `lsp`, `git` or `dap`.
- `settings` is a trap. It pulls in `fs`, which pulls in Zed's `git`, `rope`, `text`, `proto` and `telemetry` crates, for 36 crates in all. Anything that depends on `settings` therefore drags in `git`: that covers `theme_settings`, `terminal`, `feature_flags`, `fs` and everything above them.
- Anything that depends on `workspace` or `picker` pulls in the whole app. That is 90 to 154 crates, including `project`, `client`, `language`, `lsp`, `rpc`, `git`, `dap` and `node_runtime`. `picker` depends on `workspace`, `project` and `language` directly, so `picker`, `command_palette`, `auto_update` and `terminal_view` are all heavy.
- Crates.io publishing is minimal and stale. `zed_extension_api` is at 0.7.0 and `gpui` at 0.2.2 (Oct 2025). No candidate UI or app crate is published.
- Third parties do depend on `ui`, `theme` and `settings` via git, but they pin them. All of them are small GPUI apps, not forks, and most pin a rev or tag.

## Method notes
- Counts are transitive internal crates, excluding the crate itself.
- Base set: 16 crates come with any gpui-dependent crate: `collections`, `derive_refineable`, `gpui_macros`, `gpui_shared_string`, `gpui_util`, `http_client`, `path`, `perf`, `refineable`, `scheduler`, `sum_tree`, `util`, `util_macros`, `zlog`, `ztracing` and `ztracing_macro`. All Apache-2.0 plus a few small helpers.
- "git" flag means Zed's own `git` crate, not the git CLI. For `fs`, `settings` and the crates above them it arrives via `fs → git`.
- Heavy flag means the crate transitively reaches any of `project`, `client`, `editor`, `language`, `lsp`, `rpc`, `call`, `channel`, `livekit_client`, `git`, `dap` or `node_runtime`.
- `call` and `livekit_client` never appear in any closure. `channel` appears only for `keymap_editor` and `agent_ui`, and `rpc` appears wherever `client` does. `collab` is not a dependency of anything here.
