# Development flow audit — 12 October 2026

Oxikube already has a software factory: a dependency-ranked GitHub Project, story worktrees,
an extensive contributor contract, local hooks, two Sonnet review passes, and multi-platform
CI/integration/nightly checks. PR evidence also names an `ultracode` workflow outside the
tracked repository. The useful improvement is a portable operating and measurement layer,
not another implementation framework.

## Evidence and method

Read-only GitHub collection covers **2026-10-03 00:00 UTC through 2026-10-12 02:45 UTC**
(exclusive cutoff): 221 PR records, of which 204 merged in the window, and 1,860 unique
workflow run IDs. The repo had 215 main-history commits at inspection. Project inspection
returned all 446 items. Code/process inspection used `origin/main` at `d8be57b4`.

The reproducible [summary](baseline.json) contains interval boundaries, counts, nearest-rank
percentiles, event-separated workflow results and limitations. The compared period summaries
are saved separately in [cohorts.json](cohorts.json), calculated by applying `metrics.summary`
to the same snapshot with narrower `since`/`until` boundaries. The raw sanitized snapshot
is local at `.factory/baseline.json`; recollection may differ as pending runs finish or runs
are retried. The collector reads all PR pages and shards Actions queries by UTC day:
[GitHub documents a 1,000-result cap on filtered Actions queries](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository).
An initial unsharded query hit that cap and was discarded from the baseline.

These are repository delivery observations, not agent productivity measurements. There is
no trustworthy task-start history, harness active time, token/cost ledger, deployment history
or escaped-defect denominator in the inspected evidence. Do not label these DORA metrics
or compare Codex and Claude performance from them.

## Inefficiencies with evidence

### 1. Review findings can arrive after merge

[PR #636](https://github.com/karan-vk/Oxikube/pull/636) explicitly says it fixes four upheld
author-review findings from #623, which was already merged. Its findings include behavioral
bugs and tests that passed with broken wiring. [#634](https://github.com/karan-vk/Oxikube/pull/634)
and [#635](https://github.com/karan-vk/Oxikube/pull/635) are also separately merged review-fix PRs.
The written two-pass policy exists; its timing is not reliably enforced.

Branch protection read on October 12 requires three checks, strict current-base status and
linear history, but no required PR review and no required conversation resolution. That is
consistent with the repository's documented settings. The same owner account posts agent
reviews, so simply requiring human approvals needs an identity/workflow decision first.

**Implemented:** the PR template now asks for tested/reviewed SHAs; factory receipts capture
the revision and dirty content; handoff guidance makes pending review visible. **Still needed:**
one merge coordinator must verify actual review completion on the applicable revision.
The new tooling does not pretend that a local JSON record enforces remote branch protection.

### 2. Integration is repeatedly re-run while work queues for review

Across the window, PR CI had 822 runs: 633 success, 63 failure, 122 cancelled and four pending.
PR integration had 480 runs: 383 success, 42 failure and 55 cancelled. In Oct 10–11 alone,
PR CI had 250 runs: 163 success, 42 failure and 45 cancelled. Thus 34.8% of that recent
CI cohort ended failed or cancelled. PR CI p50 elapsed time in that cohort was 21.8 minutes,
p90 31.7 minutes.

Cancellation is partly intentional: both workflows cancel superseded PR runs. Failure can
be product, environment or test failure; the counts do not establish flakiness. Strict
up-to-date checks plus frequent merges are a plausible source of repeated integration,
but run history alone does not tell us which pushes were rebases versus substantive fixes.

**Implemented:** event-separated metrics and timed gate receipts. **Trial:** cap review-ready
work at three stories per integration lane; one coordinator chooses merge order, and workers
update against current main when entering that lane. Batch local fixes before pushing.
Preserve strict checks. Measure again after seven complete days before increasing capacity.

### 3. Nightly failures have become a persistent signal

Scheduled nightlies: nine runs, **one success, seven failures, one cancelled**. Manual nightlies:
38 runs, 11 success, 15 failure, 12 cancelled. The latest five nightly runs at inspection failed.
The [latest inspected run](https://github.com/karan-vk/Oxikube/actions/runs/38130766310) failed in
release tests on both platforms, macOS screenshot tests, macOS perf smoke and Linux perf budgets.

PR checks cannot be treated as proof of these nightly-only properties. Persistent red also
makes new regressions harder to distinguish. Root causes were not diagnosed in this factory
task; increasing retries or removing tests would not be evidence-based remediation.

**Next repair work:** assign each distinct failure signature an owner, reproduce it, compare
against main and repair it. Require a green nightly for the repaired signature before
resuming affected feature expansion. Use the existing diagnostic artifacts and perf budgets.

### 4. Verification evidence drifts from the final change

[PR #665](https://github.com/karan-vk/Oxikube/pull/665) candidly records that the full workspace
test run failed and was not repeated after final edits, while its checklist marks the workspace
test item complete with a qualification. This does not prove the merged code is broken; it
does show that checkbox status alone cannot answer what revision passed which checks.

**Implemented:** gate receipts bind each command's exit and duration to HEAD plus a content
fingerprint, invalidate success if content changes during the run, and keep targeted/fast/full
checks distinct. The final PR must state what remains unverified. CI remains authoritative.

### 5. The factory is portable in principle but its working state is not

Instructions repeat across `AGENTS.md`, `CLAUDE.md` and a Claude-directory contributor skill.
The important contract is readable by any harness, but task resume state, executable gates
and delivery metrics were not standardized in tracked tooling. Existing PR bodies mention
an external multi-pass `ultracode` workflow whose configuration and costs are not present here.

**Implemented:** one stdlib CLI, JSON task packets, exclusive local claims across worktrees,
explicit handoffs, and prompts for Codex, Claude or any other harness. Entry points link to
one operating guide. Existing contributor/review policy remains intact. No extra agent fan-out
is prescribed: whether the external review workflow is worth its cost needs actual cost and
finding-yield measurements.

### 6. Dependency maintenance creates additional activity

282 of the 1,860 recorded workflow runs are Dependabot update jobs. Four separate dependency
PRs remained open at inspection; `.github/dependabot.yml` schedules weekly updates but has
no grouping policy. This is a candidate for grouping compatible dependency updates and using
a scheduled integration slot. Those counts do not measure compute expense or prove redundant
work. GPUI and ACP exclusions must remain; grouping merits a separately reviewed change.

## What changed and what remains

The [operating guide](README.md) documents the commands and limits. The implementation adds
repeatable metrics, worktree claims, handoffs and revision-bound gate receipts; integrates
its deterministic tests into the existing CI lint job; and makes review/test revision evidence
explicit in the PR template. It does not alter required-check names, merge protections,
application architecture, Sonnet policy or feature scope.

Initial success criteria for the next seven-day trial: fewer failed/cancelled PR CI runs,
lower PR-open-to-merge p90 with comparable story sizes, no post-merge author-review fixes,
and recovery of scheduled nightly health. Record story claim time and blocked intervals in
handoffs for future lead-time analysis. Claim timestamps are instrumented going forward;
historical implementation time and harness efficiency remain unknown.
